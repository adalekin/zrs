# Design

## Context

Мотивация и объём описаны в `proposal.md`, поведение в `specs/`. Здесь только то, на чём стоят решения.

- Репозиторий пуст: кода и принятых спек нет.
- Проект будет открытым, поэтому зависимости берутся только из публичных реестров, а в коде нет имён организаций, провайдеров и площадок.
- `approck-services` 1.1.0, `approck-sqlalchemy-utils` 0.2.2 и `approck-fastapi-utils` 0.2.1 опубликованы на pypi.org под лицензией MIT (https://pypi.org/project/approck-services/, https://pypi.org/project/approck-sqlalchemy-utils/, https://pypi.org/project/approck-fastapi-utils/, прочитано 06.10.2026).
- У `approck-services` есть extra `upload` с зависимостью `aioboto3` (поле `requires_dist` на той же странице pypi.org).
- `approck_sqlalchemy_utils.model.Base` версии 0.2.2 на Python 3.13 ломает внешние ключи ошибкой `NoReferencedTableError`, на 3.12 работает.
- `approck_sqlalchemy_utils.session.init` версии 0.2.2 строит синхронный движок из адреса `postgresql://` без имени драйвера. SQLAlchemy 2.1 выбирает для такого адреса драйвер psycopg 3, а extra `postgres` пакета ставит psycopg2 (`session.py`, ошибка `No module named 'psycopg'` при запуске на SQLAlchemy 2.1.3).
- `validation_exception_handler` из `approck-fastapi-utils` 0.2.1 отдаёт `exc.errors()` в JSON как есть и падает на `Decimal` в контексте ошибки (`exception_handlers.py`, воспроизводится запросом с суммой `0` при ограничении `gt=0`).
- Образ `minio/minio` в Docker Hub отсутствует: `https://hub.docker.com/v2/repositories/minio/minio/` отвечает 404 (06.10.2026). SeaweedFS 4.48 поднимает S3-шлюз командой `weed server -s3 -s3.config=<файл>` (https://github.com/seaweedfs/seaweedfs/wiki/S3-Configuration).
- next-auth 4 описывает произвольного провайдера OpenID Connect опциями `wellKnown` и `idToken` (https://next-auth.js.org/configuration/providers/oauth, раздел «Using a custom provider»).
- RFC 9068 (раздел 2.2) называет обязательными в токене доступа формата JWT поля `iss`, `exp`, `aud`, `sub`, `client_id`, `iat` и `jti`. Имени и почты среди них нет (https://www.rfc-editor.org/rfc/rfc9068.txt).
- Сведения о человеке по токену доступа отдаёт UserInfo Endpoint провайдера, его адрес лежит в документе discovery в поле `userinfo_endpoint` (OpenID Connect Core 1.0, раздел 5.3, https://openid.net/specs/openid-connect-core-1_0.html).
- PyJWT сверяет `iss` и `aud` параметрами `issuer` и `audience` функции `jwt.decode` (https://pyjwt.readthedocs.io/en/stable/usage.html).
- Встроенный в PyJWT `PyJWKClient` загружает ключи блокирующим `urllib.request` (`jwt/jwks_client.py`). Набор ключей из уже полученного JSON строит `PyJWKSet.from_dict`, ключ по `kid` отдаёт `PyJWKSet.__getitem__` (`jwt/api_jwk.py`).

## Goals / Non-Goals

**Goals:**

- Один набор образов для любой установки, различия только в настройках.
- Правила согласования записаны в одном месте и проверяются одинаково из API и интерфейса.
- Сервис сам проверяет вход и не полагается на прокси перед собой.

**Non-Goals:**

- Движок произвольных процессов: статусы и переходы зашиты в коде.
- Поддержка провайдеров, которые не выдают токен доступа в формате JWT.

## Decisions

### 1. Структура репозитория

Два приложения в одном репозитории.

```
server/     Python-сервис: API, правила согласования, миграции
  cmd/http/main.py
  internal/app/ config/ controller/http/v1/ service/ entity/ dto/ exceptions.py
  migrations/
  tests/
  docker/Dockerfile
web/        веб-интерфейс на Nuxt
  app/ server/ shared/ i18n/locales/
  Dockerfile
compose.yaml   локальный запуск всего проекта для разработки
deploy/
  compose.yaml   пример боевой установки
  helm/zrs/
.github/workflows/
openspec/
```

Так же названы части у Immich: папки `server/` и `web/`, образ `immich-server` (https://github.com/immich-app/immich, `docker/docker-compose.yml`).

Слои бэкенда: контроллер принимает запрос и не обращается к базе, сервис держит правила, сущность описывает таблицу, DTO описывает контракт API.

Отклонено: один серверный процесс, который и рисует страницы, и хранит данные. API нужен отдельно, чтобы правила согласования проверялись в одном месте и были доступны без интерфейса.

### 2. Стек

- Бэкенд: Python 3.12, FastAPI, SQLAlchemy с asyncpg, Alembic, PostgreSQL, пакеты `approck-*`, зависимости через `uv`.
- Фронтенд: Nuxt 4, TypeScript, Tailwind, компоненты shadcn-vue, `@nuxtjs/i18n`, `@sidebase/nuxt-auth` поверх next-auth 4.

Сервисы над сущностями строятся на `make_service_type(Model, Filter)` из `approck_services`, сессия и транзакции берутся из `approck_sqlalchemy_utils`, ошибки наследуют `CustomException` из `approck_fastapi_utils`.

Два места обходят найденные в пакетах дефекты из раздела Context. В зависимости добавлен `psycopg`, миграции Alembic идут через него же. Обработчик ошибок валидации запроса свой: он пропускает ошибки через `jsonable_encoder`.

Отклонено: FastAPI и SQLAlchemy без `approck-*`. Сессии, базовый сервис и обработчики ошибок пришлось бы написать заново, а пакеты публичные и под MIT.

### 3. Идентификаторы и подписи

В коде, базе и API живут английские идентификаторы, подписи на русском и английском лежат в локалях фронтенда.

| Идентификатор | Подпись (ru) |
|---|---|
| Роль `requester` | Сотрудник |
| Роль `moderator` | Модератор |
| Роль `finance_director` | Финансовый директор |
| Роль `payer` | Исполнитель выплаты |
| Статус `new` | Новая |
| Статус `returned` | Ошибка |
| Статус `escalated` | Отмодерировано |
| Статус `approved` | Одобрено |
| Статус `paid` | Оплачено |
| Статус `rejected` | Отказ |
| Поле `situation` | Ситуация |
| Поле `solution` | Решение |
| Поле `payment_period` | Период оплаты |

Отклонено: подписи в базе или в настройках установки. Организация, которой нужны свои слова, правит файл локали.

### 4. Жизненный цикл: таблица переходов

Паттерн: конечный автомат, заданный таблицей. Одна таблица в сервисе запросов перечисляет переходы.

| Действие | Из | В | Кто |
|---|---|---|---|
| `resubmit` | `returned` | `new` | автор |
| `cancel` | `new`, `returned`, `escalated`, `approved` | `rejected` | автор |
| `approve` | `new` | `approved` | модератор запроса |
| `escalate` | `new` | `escalated` | модератор запроса |
| `return` | `new` | `returned` | модератор запроса |
| `reject` | `new` | `rejected` | модератор запроса |
| `approve` | `escalated` | `approved` | финансовый директор |
| `return` | `escalated` | `returned` | финансовый директор |
| `reject` | `escalated` | `rejected` | финансовый директор |
| `pay` | `approved` | `paid` | исполнитель выплаты |

«Финансовый директор» в колонке «Кто» означает человека с этой ролью, который в запросе не автор и не модератор.

Один метод применяет переход: находит строку таблицы по действию и текущему статусу, проверяет, что человек подходит под колонку «Кто», меняет статус. Список доступных человеку действий API отдаёт вместе с запросом из той же таблицы, поэтому интерфейс не повторяет правила.

Отказ в действии различает два случая. Если в таблице нет ни одной строки, где это действие доступно человеку по его отношению к запросу, ответ 403. Если такая строка есть, но для другого статуса, ответ 409 с текущим статусом. Модератор запроса, который утверждает запрос в статусе `escalated`, получает 409, исполнитель выплаты с тем же действием получает 403.

Отклонено:

- паттерн State с классом на статус: шесть статусов и десять переходов читаются таблицей, классы размазали бы их по шести файлам;
- проверки в каждом обработчике: правило «кто и из какого статуса» оказалось бы в десяти местах.

### 5. Транзакция действия

Паттерн: Unit of Work. Действие выполняется в одной транзакции: строка запроса блокируется `SELECT … FOR UPDATE`, по таблице проверяется переход, меняется статус, в журнал добавляется запись. Второе действие, пришедшее одновременно, ждёт блокировку, видит новый статус и получает отказ.

Отклонено: оптимистичная блокировка номером версии. Клиенту пришлось бы повторять запрос, а действий над одним запросом мало, и ожидание блокировки ничего не стоит.

### 6. Журнал

Таблица только на добавление. Запись создают два места: метод перехода и метод комментария. В API нет операций изменения и удаления записи. Запись хранит человека, время, статус запроса после действия, признак смены статуса и текст.

Отклонено: вывод журнала из общей таблицы аудита. Журнал входит в продуктовое поведение и показывается пользователю, ему нужна своя сущность.

### 7. Видимость

Паттерн: Specification. Один объект строит условие выборки по человеку и его ролям: автор, выбранный модератор, либо роль `finance_director` или `payer`. Им пользуются и список, и чтение одного запроса, и вложения, и журнал. Запрос, не прошедший условие, не найден.

Ответы API:

| Случай | Статус |
|---|---|
| Запрос не виден или не существует | 404 |
| Запрос виден, роль не даёт действия | 403 |
| Действие не подходит текущему статусу | 409, в теле текущий статус |
| Неверные или неполные поля | 422, в теле имя поля |
| Нет подтверждения входа или оно не прошло проверку | 401 |

Ошибка поля несёт в `type` стабильный код правила: `required`, `currency_not_allowed`, `moderator_is_author`, `not_a_moderator`, `reference_list_empty`, `reference_item_inactive`, либо код проверки схемы (`missing`, `string_too_short`, `greater_than` и другие). Остальные ошибки несут код в поле `code`. Тексты сервера английские. Интерфейс показывает свой текст на языке установки по коду, а для неизвестного кода текст сервера.

Отклонено:

- проверка доступа после загрузки запроса по идентификатору: список и карточка могли бы разойтись в правилах;
- тексты ошибок на языке установки с сервера: язык выбирает интерфейс, а у API бывают и другие клиенты.

### 8. Проверка входа на бэкенде

Бэкенд сам проверяет токен доступа из заголовка `Authorization: Bearer`. Документ `/.well-known/openid-configuration` издателя и ключи JWKS он загружает через `httpx` и держит набор ключей в памяти как `PyJWKSet`. Токен с неизвестным `kid` вызывает одну повторную загрузку ключей. На каждом запросе `jwt.decode` проверяет подпись, `iss`, `aud` и срок действия. `aud` сверяется с `OIDC_AUDIENCE`: это поле обязательно по RFC 9068, и провайдера настраивают так, чтобы он клал в него значение установки.

Отклонено:

- доверие заголовку с разобранным токеном от прокси: без такого прокси заголовок подставит любой клиент;
- проверка токена запросом к провайдеру: сетевой вызов на каждый запрос, и такая точка есть не у всех провайдеров;
- `PyJWKClient`: его блокирующая загрузка ключей останавливает цикл событий асинхронного сервиса.

### 9. Роли из сведений провайдера

Паттерн: Anti-corruption layer. Один класс переводит сведения из токена в роли сервиса. Настройки задают место списка ролей и значение на каждую из четырёх ролей. Место сначала ищется как поле верхнего уровня с таким именем (`groups`, `https://example.com/roles`), затем как путь через точку во вложенные объекты (`resource_access.zrs.roles`). В поле лежит список строк или одна строка. Остальной код знает только идентификаторы из решения 3.

Человек опознаётся по `sub`.

Отклонено: поддержка конкретных провайдеров отдельными адаптерами. Путь и четыре значения покрывают и роли приложения, и группы.

### 10. Список людей

Таблица людей: `sub`, имя, почта, роли, время выпуска последнего учтённого токена. Зависимость, которая проверяет токен, обновляет строку человека, когда `iat` токена новее сохранённого: роли берёт из токена, имя и почту из полей `name` и `email` ответа UserInfo Endpoint. Получается один вызов провайдера и одна запись в базу на выпуск токена, а не на запрос. Человек без строки и без ролей в таблицу не попадает. Человек со строкой, потерявший все роли, получает в ней пустой список ролей.

Если UserInfo Endpoint не ответил, а строка человека уже есть, запрос выполняется с прежними именем и почтой, время токена не сохраняется, и следующий запрос повторит вызов. Если строки ещё нет, запрос получает 503: человек без имени в список не попадает.

Права на действия проверяются по ролям из токена. Таблица людей служит для выбора модератора и показа имён.

Отклонено:

- чтение людей из административного API провайдера: оно у каждого провайдера своё и требует отдельных прав;
- имя и почта из токена доступа: провайдер не обязан их туда класть;
- передача имени с фронтенда: бэкенд принял бы на веру то, что прислал клиент.

### 11. Сумма и валюта

Сумма хранится числом с фиксированной точкой `NUMERIC(20, 4)`, валюта трёхбуквенным кодом. В API сумма передаётся строкой с десятичной точкой. Интерфейс форматирует сумму средствами `Intl.NumberFormat` по коду валюты.

Отклонено: целое число минимальных единиц. Число знаков у валют разное, и таблицу знаков пришлось бы держать и на бэкенде, и на фронтенде.

### 12. Справочники

Одна сущность на три справочника: вид (`operation_type`, `payment_form`, `priority`), название, признак «включено». Название уникально внутри вида. Запрос ссылается на значение по идентификатору, поэтому переименование видно и в старых запросах.

Отклонено: три таблицы. Поведение справочников одинаковое, три набора одинаковых операций ничего не дают.

### 13. Вложения

Паттерн: Adapter. Файлы лежат в S3-совместимом хранилище, загрузку ведёт сервис на `BaseUploadService` из `approck_services`. Файл отдаёт бэкенд после проверки видимости запроса, прямых ссылок на хранилище клиент не получает.

Отклонено:

- локальный диск: файлы не переживают пересоздание контейнера и не видны второй реплике;
- временные ссылки на хранилище: ссылка работает у любого, кому её переслали.

### 14. Настройки

Настройки читаются из переменных окружения через `pydantic-settings`. У перечисленных ниже значений по умолчанию нет: без любой из них процесс завершается при запуске и называет переменную.

| Переменная | Что задаёт |
|---|---|
| `OIDC_ISSUER` | адрес издателя |
| `OIDC_AUDIENCE` | ожидаемое значение `aud` токена доступа |
| `OIDC_ROLES_CLAIM` | путь к списку ролей в токене |
| `ROLE_REQUESTER`, `ROLE_MODERATOR`, `ROLE_FINANCE_DIRECTOR`, `ROLE_PAYER` | значение провайдера для каждой роли |
| `CURRENCIES` | коды валют через запятую |
| `ATTACHMENT_MAX_BYTES` | предельный размер файла |
| `S3_ENDPOINT_URL`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_REGION` | хранилище вложений |
| `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME` | база данных |

Фронтенд получает `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`, `AUTH_SECRET`, `AUTH_ORIGIN`, `API_URL` и `UI_LOCALE` (`ru` или `en`). `AUTH_ORIGIN` задаёт публичный адрес интерфейса без пути. Настройки читаются из окружения при запуске процесса, а не при сборке образа. Список валют фронтенд берёт у API.

### 15. Вход в интерфейсе и обращение к API

Паттерн: Backend for Frontend. Вход ведёт серверная часть Nuxt через `@sidebase/nuxt-auth` с провайдером next-auth, описанным опцией `wellKnown`. Вендорных провайдеров и чтения вендорных полей нет: из ID-токена берётся только `sub`, имя и роли интерфейс получает от сервера через `/v1/me`.

- Страница без сессии отправляет на маршрут `GET /sign-in`. Он внутри процесса делает два вызова next-auth (CSRF-токен и начало входа) и отдаёт браузеру адрес провайдера. Так человек попадает к провайдеру без промежуточной страницы next-auth.
- Токены доступа, обновления и ID-токен лежат в зашифрованной cookie сессии с признаком `httpOnly`: скриптам страницы они недоступны, и в ответ `/api/auth/session` они не входят. Cookie с тремя токенами превышает предел одной cookie и разбивается на части. Отдельный серверный слой упорядочивает части перед чтением: next-auth 4.21 склеивает их в порядке заголовка.
- Токен доступа обновляется по токену обновления при чтении сессии: при загрузке страницы, раз в минуту, при возврате во вкладку и один раз после ответа 401. Отказ провайдера в обновлении завершает сессию.
- Браузер обращается к `/api/v1/**` того же адреса. Серверный маршрут Nuxt добавляет заголовок `Authorization`, убирает cookie и передаёт запрос серверу на `/v1/**`. Сам маршрут токен не обновляет.
- Выход идёт формой `POST /sign-out`: сессия удаляется, браузер уходит на `end_session_endpoint` провайдера с `id_token_hint` и возвращается на главную.
- Данные API запрашиваются только в браузере. Сервер Nuxt отдаёт каркас страницы и язык.
- Человек без ролей видит отдельную страницу «Нет доступа» с выходом: интерфейс показывает её по ответу 403 на `/v1/me`.

Отклонено: браузер обращается к бэкенду напрямую с токеном. Токен оказался бы доступен скриптам страницы, а установке понадобились бы второй публичный адрес и настройка CORS.

### 16. Форма API

`POST` создаёт объект и выполняет действие, `PATCH` меняет один объект, `DELETE` удаляет.

| Маршрут | Назначение |
|---|---|
| `GET /v1/me` | человек, его роли, список валют, предел размера вложения |
| `GET /v1/users?role=moderator` | люди для выбора модератора |
| `GET /v1/requests` | список с отбором `status` и `awaiting_me`, страницы через `page` и `size` |
| `POST /v1/requests` | подать запрос |
| `GET /v1/requests/{id}` | запрос, его журнал и доступные действия |
| `PATCH /v1/requests/{id}` | правка полей |
| `POST /v1/requests/{id}/{action}` | `approve`, `escalate`, `return`, `reject`, `resubmit`, `cancel`, `pay` |
| `POST /v1/requests/{id}/comments` | комментарий |
| `POST /v1/requests/{id}/attachments` | добавить файл |
| `GET /v1/requests/{id}/attachments/{attachment_id}` | скачать файл |
| `DELETE /v1/requests/{id}/attachments/{attachment_id}` | удалить файл |
| `GET /v1/reference-items?kind=` | значения справочника |
| `POST /v1/reference-items` | добавить значение |
| `PATCH /v1/reference-items/{id}` | переименовать, выключить, включить |

Действия над запросом принимают необязательный комментарий, `pay` дополнительно принимает дату оплаты. `{action}` описан перечислением: неизвестное действие получает 422 и не пересекается с маршрутами `comments` и `attachments`.

### 17. Поставка

- Два Docker-образа: `zrs-server` и `zrs-web`.
- `compose.yaml` в корне служит разработке: `docker compose up` из корня собирает `server/` и `web/` из исходников и поднимает рядом PostgreSQL, S3-совместимое хранилище и тестового провайдера OpenID Connect с готовыми клиентом, четырьмя ролями и пользователями. Миграции выполняет отдельная служба `migrate` командой `alembic upgrade head` перед запуском сервера.
- В корневом `compose.yaml` хранилищем служит SeaweedFS, тестовым провайдером Keycloak с импортом realm из `dev/keycloak/`. Провайдер доступен под именем `keycloak.localhost:8085` и из браузера, и из контейнеров: одно имя и один порт дают одинаковый `iss` на обеих сторонах. На адрес `127.0.0.1` публикуются `web` (3300), провайдер (8085) и PostgreSQL (54320). Порт PostgreSQL нужен тестам сервера, которые идут с хоста в базу `zrs_test`.
- `deploy/compose.yaml` показывает боевую установку: опубликованные образы и PostgreSQL. Провайдер входа и S3-совместимое хранилище в него не входят, их адреса задаются переменными. Каждая переменная обязательна, без неё Compose называет её имя.

Отклонено: один файл с `compose.override.yaml` для разработки. Compose читает `compose.override.yaml` сам, без флагов (https://docs.docker.com/compose/how-tos/multiple-compose-files/merge/), и тестовый провайдер попал бы в боевой запуск.
- `deploy/helm/zrs` ставит те же образы в Kubernetes: два Deployment, два Service, Job с миграциями, необязательный Ingress. PostgreSQL и хранилище чарт не поднимает, их адреса задаются значениями.
- Job с миграциями обычный, без хуков Helm, с номером ревизии релиза в имени. Порядок держит проба готовности сервера: `/health/ready` отвечает 200, когда ревизия схемы в базе не меньше ревизии, с которой собран образ. Новые поды получают трафик после миграции, старые остаются готовыми, пока идёт выкат. Номера ревизий Alembic идут подряд (`0001`, `0002`), поэтому сравниваются как числа.
- Значения чарта: адреса и теги образов, все настройки из решения 14, тип Service и `nodePort`, `podAnnotations` и `podLabels` отдельно для каждого Deployment и для Job миграций, `imagePullSecrets`. Секреты задаются либо значениями, либо именем существующего Secret.

Отклонено:

- ресурсы конкретного ingress-контроллера или service mesh в чарте: маршрутизацию своего кластера установка описывает у себя поверх Service;
- Job миграций хуком `pre-upgrade`: хук запускается раньше, чем создан Secret релиза, и настройки пришлось бы дублировать в ресурсах-хуках;
- миграции в init-контейнере сервера: под service mesh у init-контейнера нет сети до старта sidecar.

### 18. Сборка и релиз

Репозиторий живёт на GitHub, сборку ведёт GitHub Actions, образы и чарт лежат в GitHub Container Registry.

|---|---|
| Репозиторий | `github.com/adalekin/zrs` |
| Образ сервера | `ghcr.io/adalekin/zrs-server` |
| Образ веб-интерфейса | `ghcr.io/adalekin/zrs-web` |
| Чарт | `oci://ghcr.io/adalekin/charts/zrs` |

Проект распространяется по лицензии MIT, файл `LICENSE` лежит в корне репозитория. Та же лицензия у пакетов `approck-*`, на которых стоит сервис.

- Проверочный workflow на каждый push и pull request: тесты `server/` на PostgreSQL, проверка типов и тесты `web/`, `helm lint`, `openspec validate`.
- Релизный workflow на git-тег `vX.Y.Z`: собирает оба образа с тегом `X.Y.Z` и публикует чарт версии `X.Y.Z` с тем же `appVersion`. Авторизация в реестре идёт встроенным `GITHUB_TOKEN`.

Отклонено:

- закрытый реестр организации: посторонняя установка не скачает из него ни образ, ни чарт;
- отдельный репозиторий для чарта: версия чарта и версия образов разошлись бы по двум релизам.

### 19. Проверки

- Бэкенд: `pytest` на живой PostgreSQL, базу `zrs_test` пересобирает `conftest` миграциями. Проверку токена тесты проходят на настоящем классе: токены подписаны своим ключом, JWKS, discovery и UserInfo отдаёт заглушка `pytest-httpx`. Тесты API подменяют проверку токена и хранилище зависимостями FastAPI и ходят только через HTTP.
- Фронтенд: проверка типов и модульные тесты серверной части: маршрут `/api/v1/**`, состав сессии для браузера, перенаправление на вход, выход, порядок частей cookie, настройки, совпадение ключей двух локалей. Страницы проверяются в браузере на корневом `compose.yaml`.
- Сквозная проверка идёт на корневом `compose.yaml` с тестовым провайдером.

### 20. Подача запроса в интерфейсе

Паттерн: модальная форма с черновиком на стороне клиента. Запрос пишется в одном диалоге: новый открывается поверх списка, правка поверх страницы запроса. Отдельных страниц у формы нет.

- Порядок и названия полей повторяют форму, с которой команда переходит: вид операции, модератор, ситуация, решение, сумма с валютой, период оплаты, форма оплаты, приоритет, дедлайн, документы на оплату. Обязательные поля отмечены звёздочкой.
- Обязательный список с единственным значением выбран сразу. Других значений по умолчанию форма не подставляет.
- Причины, по которым запрос подать нельзя (пустой справочник видов операций или приоритетов, нет ни одного модератора), форма называет при открытии и не даёт отправить запрос.
- Незаконченный ввод хранится в `sessionStorage` вкладки под ключом с идентификатором человека и запроса: он переживает закрытие диалога и перезагрузку страницы и удаляется после отправки или сброса. Это относится и к новому запросу, и к правке. Выбранные файлы переживают закрытие диалога, но не перезагрузку страницы. Щелчок мимо диалога не закрывает начатый запрос.
- У возвращённого запроса диалог правки показывает над формой комментарий, с которым запрос вернули.
- Документы нового запроса выбираются в той же форме. У существующего запроса документы добавляются и удаляются на его странице, в диалоге правки их нет. Интерфейс создаёт запрос и затем загружает файлы по одному. Файл больше предела установки отсекается до отправки. Если загрузка не прошла, человек попадает на страницу запроса с перечнем незагруженных файлов.
- После подачи человек остаётся в списке: список обновляется, уведомление называет номер запроса и модератора и ведёт на страницу запроса.
- Ошибки сервера показываются у полей, курсор встаёт в первое поле с ошибкой. Сумма после ввода разбивается на разряды и читается по правилам языка установки; текст, который не похож на число этого языка, уходит серверу как есть и возвращается ошибкой у поля.

Отклонено:

- отдельные страницы подачи и правки: человек теряет список или страницу запроса и возвращается лишним переходом;
- подтверждение при закрытии диалога: лишний вопрос там, где черновик и так сохраняется;
- создание запроса и загрузка файлов одним вызовом API: потребовало бы второго формата запроса на создание при том же результате.

### 21. Интерфейс как очередь

Паттерн: рабочая очередь (Worklist). Сервис не отправляет уведомлений, поэтому каждый экран отвечает на два вопроса: что нужно от меня и у кого сейчас запрос.

- Список запросов открывается вкладкой «Ждут меня» со счётчиком, если в ней есть запросы, иначе вкладкой «Все». Выбранная вкладка, отбор по статусу и страница лежат в адресе. Отбор по статусу есть только на вкладке «Все».
- Строка списка показывает вид операции, первую строку ситуации, сумму, статус и сторону, у которой запрос: автор, модератор, финансовый директор или исполнитель выплаты. Сторона выводится из статуса. Пометку «ждёт вас» строка получает, если запрос входит в ответ API с отбором `awaiting_me`; правило очереди интерфейс не повторяет.
- Цвет принадлежит статусу: у каждой стороны, чей сейчас ход, свой оттенок, завершённые статусы нейтральны. Основной цвет интерфейса отдан главному действию экрана и пометке «ждёт вас».
- Страница запроса делится на две части: слева запрос (сумма, путь по сторонам, ситуация, решение, поля, документы), справа решение (панель с действиями, журнал, комментарий). В панели залито одно действие, которое двигает запрос вперёд; действия, которые его останавливают, стоят отдельно. Тому, кто действовать не может, панель называет сторону, у которой запрос. Причину возврата или отказа панель показывает словами того, кто решил.
- Пустые состояния говорят, что делать: сотруднику без запросов предлагают подать первый, человеку с пустой очередью говорят, что появится в очереди.
- На экране уже 640 px список показывается карточками, страница запроса складывается в одну колонку.

Отклонено:

- вкладка «Мои»: у API нет отбора по автору, а сотрудник без других ролей и так видит только свои запросы;
- вычислять «ждёт вас» в интерфейсе по ролям человека: правило очереди уже есть на сервере, вторая копия разошлась бы с ним.

## Risks / Trade-offs

- [Провайдер выдаёт непрозрачный токен доступа, а не JWT] → README называет требование к провайдеру: токен доступа в формате JWT со списком ролей. При таком токене API отвечает 401 и пишет причину в лог.
- [Провайдер по умолчанию не кладёт значение установки в `aud` токена доступа] → README описывает настройку `aud` у провайдера, тестовый провайдер в корневом `compose.yaml` настроен так же. При чужом `aud` API отвечает 401 и пишет в лог полученное и ожидаемое значения.
- [Cookie сессии с тремя токенами занимает несколько килобайт и может превысить предел заголовков у прокси перед интерфейсом] → README советует поднять этот предел у прокси.
- [UserInfo Endpoint провайдера недоступен] → люди, которые уже входили, продолжают работать с прежними именами, новый человек получает 503 до восстановления провайдера.
- [Роль сняли у провайдера, а в списке людей она осталась до следующего входа человека] → права на действия проверяются по токену, список влияет только на выбор модератора. Автор меняет модератора, пока запрос в статусе `new`.
- [В организации один финансовый директор, и переданный ему запрос подал он сам или он же в нём модератор] → такой запрос одобрить некому. Модератор утверждает запросы финансового директора сам, без передачи, а автор отменяет зависший запрос и подаёт заново.
- [Модератор ушёл из организации, а запросы ждут его решения] → автор меняет модератора или отменяет запрос. Отдельного переназначения нет.
- [На новой установке справочники пусты] → подача запроса отвечает ошибкой с названием справочника, README советует финансовому директору войти первым.
- [Блокировка строки держится, пока идёт запись в журнал] → транзакция действия не делает сетевых вызовов: хранилище и провайдер в ней не участвуют.
- [Файл загружен в хранилище, а транзакция с записью о нём откатилась] → объект в хранилище остаётся без записи. Загрузка идёт до записи в базу, и осиротевший объект ни к одному запросу не привязан и никому не виден.
