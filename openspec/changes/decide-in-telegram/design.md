# Design

## Context

Мотивация и объём описаны в `proposal.md`, поведение в `specs/`. Здесь только то, на чём стоят решения.

- Действие над запросом выполняет один метод: `ExpenseRequestService.act` принимает действующее лицо `Actor`, находит переход по таблице и пишет журнал в той же транзакции (`server/internal/service/expense_request.py`, `server/internal/service/transitions.py`).
- `Actor` это человек и роли из его текущего подтверждения входа; его собирает `get_actor` для каждого запроса к API (`server/internal/service/actor.py`, `server/internal/controller/http/deps.py`).
- Сервис хранит роли человека на момент последнего входа; права проверяются по подтверждению входа, а не по этой записи (`server/internal/entity/person.py`; требование «Список людей» в `openspec/specs/access-and-roles/spec.md`).
- Какие действия доступны человеку над запросом, отдаёт `available_actions` по той же таблице переходов (`transitions.py`).
- Комментарий к решению необязателен (`ActionRequest.comment` в `server/internal/dto/expense_request.py`).
- Привязка чата к человеку, шлюз `TelegramGateway`, задача приёма обновлений и классы видов сообщений заданы изменением `notify-by-telegram` (решения 2, 5, 6 и 7).
- Сообщение «запрос ждёт действия» получают только люди, в чьём отборе запрос стоит (изменение `notify-by-telegram`, решение 3).
- Кнопки под сообщением бота не отправляют сообщений в чат: бот получает обновление `callback_query` и отвечает на него вызовом `answerCallbackQuery`; клавиатуру под сообщением можно менять (https://core.telegram.org/bots/features, разделы «Inline Keyboards» и «Status alerts», прочитано 09.10.2026).
- Данные кнопки занимают от 1 до 64 байт (https://core.telegram.org/bots/api, поле `callback_data` объекта `InlineKeyboardButton`, прочитано 10.10.2026).
- Сообщение можно отправить ответом на другое сообщение чата (объект `ReplyParameters` там же).
- `atomic` из `approck_sqlalchemy_utils` на внешнем уровне открывает и фиксирует транзакцию, а вложенный работает точкой сохранения: сбой внутри откатывает только свой блок (`approck_sqlalchemy_utils/transaction.py`).

## Goals / Non-Goals

**Goals:**

- Решение из Telegram проходит тот же путь, что решение из сервиса: та же таблица переходов, та же запись журнала.
- Кнопка не может выполнить действие, которого человеку не предлагали.
- Состояние разговора с ботом переживает перезапуск сервера и не зависит от реплики.

**Non-Goals:**

- Оплата, повторная подача, отмена и правка запроса из Telegram.
- Назначение исполнителя выплаты при одобрении из Telegram: исполнитель остаётся тем, что был.
- Пометка в журнале о том, что решение принято в Telegram.
- Подтверждение личности при каждом решении.

## Decisions

### 1. Решение из Telegram идёт через тот же сервис

Паттерн: Service Layer (Fowler, PoEAA). У действия над запросом один вход, `ExpenseRequestService.act`, и два транспорта: HTTP и бот. Обработчик нажатия собирает `Actor` из записи о человеке и вызывает тот же метод. `Actor` получает второй способ создания, `Actor.as_last_signed_in(person)`, по сохранённым ролям человека, рядом с существующим созданием по подтверждению входа; правила перехода и запись журнала не знают, откуда пришло действие. Чтение обновлений идёт одной транзакцией, и `act` внутри неё становится точкой сохранения: отказ в действии откатывает только его.

Отклонено:

- отдельная логика решений для бота: правила согласования были бы записаны дважды;
- обращение бота к собственному HTTP API сервера: у бота нет токена человека, а выпускать токены сервис не умеет.

### 2. Кнопка несёт одноразовое намерение

Паттерн: Command, сохранённая до исполнения. Когда сообщение отправляется, для каждой кнопки в базе создаётся намерение: человек, запрос, действие, состояние. Кнопка несёт только случайный токен намерения, 22 знака; две кнопки под вопросом о причине добавляют к нему слово. Обработчик нажатия находит намерение, сверяет его чат с чатом нажавшего и исполняет. Исполненное и отменённое намерение второй раз не исполняется.

Набор кнопок берётся из `available_actions` для получателя, пересечённого со списком решений согласования; правило «что доступно» остаётся в таблице переходов.

Отклонено: номер запроса и действие в данных кнопки. Человек мог бы прислать данные кнопки, которой ему не показывали, а размер таких данных ограничен.

### 3. Разговор о причине это состояние намерения

Паттерн: State. Намерение возврата или отказа после нажатия переходит в состояние «ждёт причину»: бот спрашивает причину и предлагает ответ без комментария и отмену. Следующее текстовое сообщение человека в этом чате становится комментарием, и намерение исполняется. У человека не больше одного намерения в этом состоянии: нажатие другой кнопки отменяет ожидание. Состояние лежит в базе, поэтому ответ может обработать любая реплика и после перезапуска. Намерение помнит номер сообщения с вопросом, чтобы убрать его кнопки, когда причина получена.

Отклонено: состояние разговора в памяти процесса. Оно терялось бы при перезапуске и не было бы видно второй реплике.

### 4. Обновления бота разбирают обработчики по видам

Паттерны: Registry и Strategy. Задача приёма обновлений из `notify-by-telegram` получает реестр обработчиков: запуск бота по ссылке, блокировка бота, нажатие кнопки, текстовое сообщение. Каждый обработчик это класс с одним методом в `server/internal/service/bot.py`; `BotListener` находит обработчик в реестре `HANDLERS` по виду события и о видах сам не знает. Привязка и отвязка из `notify-by-telegram` становятся двумя такими обработчиками. Обработчик меняет базу в транзакции чтения, а ответы человеку кладёт на `Desk`: их отправляют после фиксации, чтобы бот не сообщил о том, чего не случилось.

Отклонено: ветки по виду обновления в цикле опроса. Цикл рос бы с каждым новым видом.

### 5. Кнопки принадлежат виду сообщения

Вид «запрос ждёт действия» из `notify-by-telegram` отдаёт вместе с текстом клавиатуру. `TelegramGateway` получает три вызова: отправить сообщение с клавиатурой, ответить на нажатие, изменить клавиатуру отправленного сообщения. После исполнения или отказа бот убирает кнопки под сообщением и пишет результат ответом на это сообщение, чтобы итог стоял рядом с запросом. Кнопки стоят по две в ряд, подписи короткие: «Утвердить», «Финдиректору», «Вернуть», «Отклонить». Вопрос о причине зависит от действия: при возврате бот спрашивает, что автору исправить, при отказе почему отклонён запрос.

### 6. Настройка

`TELEGRAM_DECISIONS` принимает `on` или `off` и обязательна при `NOTIFICATIONS=telegram`; значения по умолчанию нет. При `off` сообщения несут только ссылку, намерения не создаются.

### 7. Веб-интерфейс

Страница «Уведомления» показывает, разрешены ли в установке решения из Telegram, и предупреждает рядом с привязкой, что из привязанного чата можно решать по запросам. Признак приходит из `GET /v1/me` вместе с остальным состоянием уведомлений.

### 8. Что меняется в существующем коде

- `Actor` получает создание по сохранённым ролям.
- Цикл приёма обновлений уходит из `TelegramLinkService` в `BotListener` с реестром обработчиков; привязка и отвязка становятся обработчиками, сервис привязки оставляет себе только привязку.
- Вид сообщения «ждёт действия» отдаёт клавиатуру; `TelegramGateway` получает три вызова.
- Шлюз запрашивает у Telegram и нажатия кнопок; текст в чате бота становится событием.
- Не трогаются: таблица переходов, `ExpenseRequestService.act`, журнал, HTTP API запросов.

## Risks / Trade-offs

- [Роль у человека сняли, а он не входил в сервис] → решение из Telegram ему доступно до следующего входа; это записано требованием, а установка включает решения из Telegram явно.
- [Чужой человек получил доступ к Telegram согласующего] → он может решать по запросам из очереди этого согласующего; оплата из Telegram не выполняется, привязка снимается в сервисе, а установка может не включать решения из Telegram.
- [По журналу не видно, что решение принято в Telegram] → запись журнала называет человека и решение; откуда оно пришло, журнал не хранит.
- [Согласующий решил в сервисе, а сообщение с кнопками осталось] → нажатие получает ответ с текущим статусом запроса, кнопки исчезают.
- [Человек написал боту текст, когда причины никто не ждал] → бот отвечает, что ждёт нажатия кнопки, и ничего не выполняет.
