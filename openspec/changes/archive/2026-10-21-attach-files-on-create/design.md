# Design

## Context

- Запрос автора с ролью модератора, не выбравшего другого модератора, создаётся в статусе `ESCALATED` (`server/internal/service/expense_request.py`, `ExpenseRequestService.create`; изменение `moderated-by-author`).
- Сервер принимает и удаляет файлы, только пока запрос в `EDITABLE_STATUSES` = {`NEW`, `RETURNED`} и действует автор (`ExpenseRequestService.lock_editable`, `transitions.EDITABLE_STATUSES`); иначе ответ 409 `StatusConflict`.
- Форма нового запроса создаёт запрос `POST /v1/requests` с JSON-телом и затем загружает каждый файл `POST /v1/requests/{id}/attachments` (`web/app/components/RequestForm.vue`, `applyDocuments`). Изменения документов в форме правки применяются тем же методом (архивный дизайн `2026-10-19-attach-files-in-edit`, решение 1).
- `AttachmentService.add` читает файл с пределом `ATTACHMENT_MAX_BYTES` (`AttachmentTooLarge`), кладёт объект в хранилище под ключом `requests/{request_id}/{uuid}` до своей транзакции и затем пишет строку `attachment`: транзакция действия не делает сетевых вызовов.
- `ExpenseRequestService.create` проверяет поля (`_validate`) до транзакции, а в транзакции пишет запрос, запись журнала и уведомление (`_announce`).
- Ключ `expense_request.id` выдаёт последовательность PostgreSQL (`autoincrement=True`, `server/migrations/versions/0001_initial_schema.py`).
- `POST /v1/requests` вызывает только веб-интерфейс ZRS (`RequestForm.vue`); бот Telegram запросы не создаёт.
- Ошибку поля веб-интерфейс берёт из 422 по последнему элементу `loc` (`web/app/utils/api-error.ts`).

## Goals / Non-Goals

**Goals:** запрос создаётся вместе с документами одной операцией в любом начальном статусе.

**Non-Goals:** правило, в каких статусах автор меняет документы существующего запроса; форма правки и её применение изменений документов.

## Decisions

### 1. Контракт: `POST /v1/requests` как `multipart/form-data` с JSON-частью `request` и частями `files`

Поля запроса передаются частью `request` в виде JSON по схеме `RequestCreate`, файлы повторяющейся частью `files` (ноль и больше). Сервер разбирает `request` той же моделью; ошибка разбора отдаётся 422 в прежнем виде (`loc` = `["body", <поле>]`), поэтому разбор ошибок полей в веб-интерфейсе не меняется. JSON-тело маршрут больше не принимает: одна операция, один контракт.

Паттерн: составное тело `multipart/form-data` (RFC 7578), где одна часть несёт структурированные данные в JSON, а в остальных лежат файлы. Тело JSON и файлы в одном запросе HTTP не совмещаются, поэтому данные запроса едут частью тела.

Отвергнуто:
- плоские поля формы: двенадцать полей с `null`, десятичной суммой и необязательными ссылками пришлось бы переводить из строк вручную, и `RequestCreate` перестал бы быть схемой тела;
- предварительная загрузка (файлы отдельным маршрутом во временное состояние, создание запроса со ссылками на них): новая сущность, её срок жизни и уборка брошенных загрузок ради формы, которая отправляет всё сразу;
- два типа тела на одном маршруте (JSON и `multipart`): два контракта одной операции и ручной разбор по `Content-Type`.

### 2. Сохранение: проверить всё, затем хранилище, затем одна транзакция

`ExpenseRequestService.create` получает файлы и выполняет шаги по порядку:

1. проверка прав и полей (`_validate`), как сейчас;
2. чтение каждого файла с пределом (`AttachmentTooLarge` до любой записи);
3. номер запроса берётся вне транзакции: `nextval(pg_get_serial_sequence('expense_request', 'id'))`;
4. объекты кладутся в хранилище под ключами `requests/{номер}/{uuid}`;
5. одна транзакция пишет запрос с этим номером, строки `attachment`, запись журнала и уведомление.

Чтение с пределом и сборка строки `attachment` выносятся из `AttachmentService.add` в общий код, которым пользуются и `add`, и создание; второй копии цикла чтения не появляется. Операцией владеет `ExpenseRequestService.create`, потому что документы входят в содержание запроса.

Паттерн: Identity Field с заранее выданным ключом (Fowler, PoEAA), чтобы ключ объекта знал номер запроса до транзакции; сама транзакция служит Unit of Work над запросом и его документами.

Отвергнуто:
- создание запроса в `NEW` с последующей эскалацией после загрузки: промежуточное состояние и лишнее действие;
- разрешить автору менять документы в `ESCALATED`: документы менялись бы, пока финансовый директор смотрит запрос;
- загрузка в хранилище внутри транзакции: сетевой вызов под блокировкой, вопреки правилу `AttachmentService.add`;
- ключ объекта без номера запроса: вторая схема ключей в одном бакете.

### 3. Веб-интерфейс: форма нового запроса отправляет поля и файлы одним обращением

`RequestForm.submit` для нового запроса собирает `FormData` (`request` и `files`) и отправляет один `POST /v1/requests`; `applyDocuments` остаётся только у правки. Перечня незагруженных файлов у нового запроса больше нет: если отклонён любой файл, не создаётся и запрос, а форма показывает ошибку и остаётся открытой. Ответ 413 `AttachmentTooLarge` (`server/internal/exceptions.py`) форма показывает сообщением с пределом из поля `limit`, тем же текстом, что `FileDropzone`; ошибки полей показываются как сейчас. Сообщение `request.filesFailed` удаляется. Предел файла по-прежнему отсекает `FileDropzone` до отправки.

## Risks / Trade-offs

- [Транзакция упала после записи в хранилище] → объекты остаются без строк в закрытом бакете, их никто не отдаёт; так же ведёт себя `AttachmentService.add`.
- [Номер, выданный последовательностью, не стал запросом] → в нумерации пропуск, как при любой откатившейся вставке.
- [Внешний клиент шлёт JSON на `POST /v1/requests`] → получает 422; других вызывающих маршрут сейчас нет, изменение помечено в proposal как BREAKING.
- [Большое тело из нескольких файлов] → предел действует на каждый файл, файлы держатся в памяти до записи, как в `add`.
