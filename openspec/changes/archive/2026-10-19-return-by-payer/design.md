# Design

## Context

- Путь запроса задан одной таблицей переходов `TRANSITIONS` в `server/internal/service/transitions.py`; API применяет действия и отдаёт доступные действия только из неё.
- Исполнитель выплаты становится стороной `Party.PAYER` запроса, назначенного ему или никому (`parties()` там же).
- Строки отмены из статусов `new`, `returned`, `escalated` не имеют условия: до этого изменения запрос с оплатой в эти статусы не попадал. Строка отмены из `approved` проверяет `without_a_payment`.
- Набор файлов автор меняет в статусах `EDITABLE_STATUSES` (`new`, `returned`).
- Веб-интерфейс строит кнопки по списку `actions` из ответа сервера; подпись `action.return` («Вернуть автору») общая для всех ролей (`web/i18n/locales/ru.json`).
- Сообщение «ждёт действия» адресовано тем, кого запрос ждёт после действия и не ждал до него, и называет того, кто вернул запрос, по записи журнала (`entry.person`, `server/internal/service/notices.py:311`; изменение `notify-by-telegram`).
- Страница запроса определяет, у кого запрос, по статусу: `returned` у автора (`web/app/utils/holder.ts:7`).
- Оплата хранит сумму в валюте запроса (`Payment.amount`, `server/internal/entity/expense_request.py:105`).
- Сообщения исполнителю выплаты в Telegram кнопок не несут (изменение `decide-in-telegram`). Кнопки предлагает `DecisionOffer.offer` в `server/internal/service/telegram_decisions.py`: решения `DECISIONS` (утвердить, вернуть, отклонить), доступные человеку по таблице переходов.

## Goals / Non-Goals

**Goals:** исполнитель выплаты возвращает одобренный запрос автору тем же действием `return`, что и согласующие.

**Non-Goals:** кнопка возврата в Telegram у исполнителя выплаты; возврат одобренного запроса финансовым директором.

## Decisions

### 1. Возврат исполнителем это строка таблицы переходов

Паттерн: табличный конечный автомат (State Machine, table-driven), который уже держит весь путь запроса. Добавляется строка `Transition(Action.RETURN, Status.APPROVED, Status.RETURNED, Party.PAYER)` без условия: возврат доступен и периодическому запросу с оплатами. Кто из исполнителей может вернуть запрос, решает `parties()`, то есть то же правило, что и для оплаты.

Отвергнуто:
- отдельное действие вроде `send_back`: поведение совпадает с возвратом согласующего (статус «Ошибка», комментарий необязателен, повторная подача), отдельное имя размножило бы подписи, обработку в Telegram и уведомления;
- проверка роли в `ExpenseRequestService.act` в обход таблицы: правило «кто, что, из какого статуса» перестало бы жить в одном месте, и список доступных действий разошёлся бы с тем, что сервер принимает.

### 2. Отмена с оплатой запрещена в каждом статусе

Строки отмены из `new`, `returned`, `escalated` получают условие `without_a_payment`, как строка из `approved`. Так требование «Отмена автором» выполняется для периодического запроса с оплатой, который после возврата проходит согласование заново.

Отвергнуто: запрет возврата периодического запроса с оплатой. Периодическому запросу счёт нужен каждый период, и именно для него возврат нужнее всего.

### 3. Кнопки решений в Telegram только на шагах согласования

`DecisionOffer.offer` предлагает кнопки только у запроса в статусах `new` и `escalated` (`DECIDED_IN`). Без этого возврат исполнителя, попав в таблицу переходов, стал бы кнопкой «Вернуть» под сообщением исполнителю, а у таких сообщений кнопок нет. Отбор по статусу, а не по стороне запроса: решения в Telegram это решения согласующих, и согласуют запрос именно в этих двух статусах.

Отвергнуто: исключить `Party.PAYER` при подборе решений. Человек с ролями финансового директора и исполнителя выплаты одной стороной не описывается, а статус однозначно говорит, идёт ли согласование.

### 4. Возврат в сервисе не получает ветвей под роль

Веб-интерфейс показывает кнопку из `actions`, подпись и форма комментария общие с возвратом согласующих. Сообщение автору о возврате пишет существующий вид «ждёт действия» с именем из записи журнала. Страница запроса показывает возвращённый запрос у автора по статусу.

### 5. Периодичность и валюта запроса с оплатой закрыты в правке

Паттерн: доменная проверка в `ExpenseRequestService.update`, рядом с `_validate`, по тому же образцу `FieldInvalid` с именем поля. Проверка срабатывает, когда у запроса есть оплата и значение `recurrence` или `currency` в теле отличается от записанного; то же значение, присланное формой целиком, проходит. Правило живёт в сервисе, а не в таблице переходов: таблица отвечает за действия и статусы, правка полей идёт мимо неё.

Форма правки (`web/app/components/RequestForm.vue`) у запроса с непустым `payments` показывает периодичность и валюту без возможности изменить: сервер всё равно отклонит смену, а форма не должна предлагать недоступное.

Отвергнуто:
- запрет любой правки полей у запроса с оплатой: автору после возврата бывает нужно поправить сумму очередного счёта;
- перенос валюты в каждую оплату: меняет схему базы и итоги ради случая, которому решение не нужно.

## Risks / Trade-offs

- [Периодический запрос с оплатами в статусе «Ошибка» выпадает из очереди исполнителя до нового одобрения] → это цель возврата: платить нечем, пока автор не приложил документ; после одобрения запрос возвращается в очередь по правилам периода.
