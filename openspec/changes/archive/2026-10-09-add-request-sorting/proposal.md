# Proposal

## Why

Запросы показаны только от новых к старым. Тот, кто согласует и платит, решает сначала срочное и то, у чего ближе дедлайн, а такие запросы приходится выискивать среди остальных. У приоритетов при этом нет порядка: сервис не знает, какой из них важнее.

## What Changes

- Финансовый директор расставляет приоритеты по важности в справочнике.
- Список запросов сортируется по приоритету, по дедлайну и по дате подачи, в обе стороны. По умолчанию он остаётся от новых к старым.
- Карточки доски идут одним выбранным порядком во всех колонках. По умолчанию по приоритету.
- Запросы без дедлайна стоят ниже запросов с дедлайном, завершённые запросы ниже запросов в работе.

## Capabilities

### New Capabilities

- `request-order`: порядок запросов в списке и на доске: по чему сортируют, как стоят равные запросы, запросы без дедлайна и завершённые.

### Modified Capabilities

- `expense-requests`: порядок списка «от новых к старым» становится порядком по умолчанию.
- `reference-lists`: у приоритетов появляется порядок, который задаёт финансовый директор.

## Impact

- Сервер: `GET /v1/requests` принимает параметр `sort`; значение справочника хранит место в порядке и отдаёт его; новый маршрут `POST /v1/reference-items/{id}/position` ставит значение на другое место. Схема базы получает одну миграцию.
- Веб-интерфейс: заголовки колонок списка, выбор порядка на доске, стрелки у приоритетов на странице «Справочники», обе локали.
- Изменение опирается на доску из `add-request-board` и применяется после него.
- Новых зависимостей нет.
