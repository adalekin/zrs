# Design

## Context

Мотивация и объём описаны в `proposal.md`, поведение в `specs/`. Здесь только то, на чём стоят решения.

- Значение справочника хранит вид, название и признак «включено». Одна сущность обслуживает три справочника (`server/internal/entity/reference_item.py`; решение 12 в `openspec/changes/archive/2026-10-08-add-expense-requests/design.md`).
- Перечисления сервера объявлены как `StrEnum` в `server/internal/entity/enums.py` и лежат в базе строками: `Role`, `Status`, `Action`, `ReferenceKind`.
- `PATCH /v1/reference-items/{id}` меняет название и признак «включено». Базовый сервис пишет в сущность только переданные поля: `model_dump(exclude_unset=True)` в `update_indirect` (`approck_services/sqlalchemy/base.py`).
- Ответ API о запросе вкладывает вид операции, приоритет и форму оплаты объектами `ReferenceItemRead` (`server/internal/dto/expense_request.py`).
- `PATCH` меняет один объект, отдельного маршрута на поле в API нет (решение 16 того же архивного `design.md`).
- Цвет в интерфейсе принадлежит статусу. Строка списка показывает вид операции, первую строку ситуации, сумму, статус и сторону, у которой запрос (решение 21 там же).
- Статус рисует компонент `StatusBadge`: круглая плашка, оттенок берётся из таблицы `TONES` по идентификатору статуса (`web/app/components/StatusBadge.vue`). Так же устроена таблица `DOTS` журнала (`web/app/pages/requests/[id]/index.vue`).
- Tailwind читает исходники как обычный текст и не видит имён классов, собранных из частей во время работы. Документация советует таблицу, которая переводит значение свойства в полные имена классов (https://tailwindcss.com/docs/detecting-classes-in-source-files, раздел «Dynamic class names», прочитано 08.10.2026).
- Notion API отдаёт цвет варианта свойства именем из закрытого списка: `default`, `gray`, `brown`, `orange`, `yellow`, `green`, `blue`, `purple`, `pink`, `red` (https://developers.notion.com/reference/property-object, таблица «Select options», прочитано 08.10.2026).
- Страница ограничена шириной 1152 px: класс `max-w-6xl` в шапке и в основном блоке `web/app/layouts/default.vue`.
- Страница запроса делит ширину на колонку запроса и панель решения шириной 22rem с отступом 2rem: класс `lg:grid-cols-[minmax(0,1fr)_22rem]` в `web/app/pages/requests/[id]/index.vue`. При странице 1152 px колонке запроса остаётся 736 px, при 1280 px она займёт 864 px.
- В макете списка с девятью колонками при ширине страницы 1152 px колонке «Запрос» остаётся 204 px, и обрезаются десять из тринадцати первых строк ситуации длиной от 29 знаков. При 1280 px колонка занимает 332 px, обрезается одна строка в 71 знак (замер 08.10.2026).
- Таблица списка лежит в контейнере с горизонтальной прокруткой (`web/app/components/ui/table/Table.vue`). На экране уже 640 px список показывается карточками (`web/app/pages/index.vue`).
- В `web/app/components/ui` нет всплывающей панели: есть диалог, поля, переключатель и таблица.
- Номера ревизий Alembic идут подряд, проба готовности сервера сравнивает их как числа (решение 17 архивного `design.md`).

## Goals / Non-Goals

**Goals:**

- Правило «как выглядит значение справочника» записано в одном месте интерфейса.
- В базу попадает только цвет из палитры.
- Оттенок значения не читается как статус.

**Non-Goals:**

- Доска запросов по статусам.
- Порядок значений в справочнике.
- Сортировка и группировка списка по значениям справочников.
- Цвет вне палитры.
- Цвет в выпадающих списках формы запроса: там остаются названия.

## Decisions

### 1. Цвет хранится полем значения справочника

Паттерн: атрибут сущности со значением из перечисления. Сущность `ReferenceItem` получает поле `color`, перечисление `ReferenceColor` встаёт рядом с `ReferenceKind` в `server/internal/entity/enums.py`. Поле допускает `NULL`: это состояние «цвета нет», а не значение по умолчанию. Новой сущности, сервиса и маршрута нет.

Отклонено:

- отдельная таблица «значение и его цвет»: связь один к одному без собственной жизни, а каждое чтение запроса получило бы лишнее соединение;
- цвета в настройках установки: значения справочников появляются во время работы, настройка не может на них сослаться;
- цвет по идентификатору значения, без выбора человеком: цвет ничего бы не значил, а смысл ему должен дать тот, кто ведёт справочник.

### 2. API передаёт имя цвета, оформление выбирает интерфейс

Паттерн: закрытое перечисление в контракте и таблица соответствия на стороне клиента. Так же сделано со статусом: API отдаёт идентификатор, оттенок выбирает таблица `TONES`.

| Имя в API | Подпись (ru) |
|---|---|
| `red` | Красный |
| `orange` | Оранжевый |
| `yellow` | Жёлтый |
| `green` | Зелёный |
| `teal` | Бирюзовый |
| `blue` | Синий |
| `violet` | Фиолетовый |
| `pink` | Розовый |

Имя называет цвет так, как его видит человек, а не оттенок из библиотеки стилей: какой оттенок рисует `yellow`, решает таблица соответствия в интерфейсе.

Имена в палитру только добавляются. Сохранённое имя лежит в базе строкой, а ответ API проверяется по перечислению, поэтому убрать или переименовать имя можно только вместе с миграцией, которая переписывает сохранённые значения.

Сервер проверяет имя схемой запроса: имя не из перечисления получает 422 с кодом проверки схемы, как любое другое поле. Интерфейс держит тот же список в `web/shared/types/api.ts` рядом со `STATUSES` и `REFERENCE_KINDS`. Две таблицы соответствия лежат в `web/app/utils/reference-color.ts`: заливка метки и кружок палитры. В них записаны полные имена классов. Названия цветов лежат в обеих локалях под ключом `color.<имя>`: палитра показывает их рядом с кружками.

Отклонено:

- код цвета (`#rrggbb`) в API: контраст названия на произвольном фоне никто не гарантирует, а интерфейс не может заранее собрать под него стили;
- имена классов оформления в API: контракт узнал бы о библиотеке стилей одного клиента;
- палитра только в интерфейсе, сервер хранит любую строку: в базе оказались бы имена, которых интерфейс не знает.

### 3. Цвет меняется и снимается тем же `PATCH`

Тело `PATCH /v1/reference-items/{id}` получает поле `color`. Поле не передано: цвет не меняется. Передано имя: цвет задан. Передан `null`: цвет снят. Это прямое следствие того, что сервис пишет только переданные поля. `ReferenceItemCreate` не меняется: значение создаётся без цвета.

Отклонено:

- отдельный маршрут для цвета: `PATCH` уже меняет один объект, второй маршрут на одно поле расходится с формой API;
- имя `none` в перечислении: «цвета нет» получило бы два способа записи, `null` и `none`.

### 4. Цвет приезжает вместе со значением

`ReferenceItemRead` получает поле `color`. Запрос в списке и на своей странице уже несёт значения справочников этим объектом, поэтому цвет приходит без новых обращений к API.

Отклонено: интерфейс отдельно загружает справочники и сопоставляет цвета по идентификатору. Каждому экрану с запросами понадобился бы второй вызов, а сопоставление повторилось бы в трёх местах.

### 5. Один компонент владеет видом значения

Паттерн: презентационный компонент. `ReferenceValue` принимает значение справочника и рисует его: у значения с цветом прямоугольная метка с заливкой и названием, у значения без цвета название обычным текстом. Состояния у компонента нет. Его используют строка списка, карточка списка на узком экране и страница запроса.

Статус остаётся за `StatusBadge` и остаётся круглой плашкой. Оттенки двух наборов частично совпадают (синий, фиолетовый, зелёный, жёлтый), их разводят форма и место: статус круглый и стоит в своей колонке, значение справочника прямоугольное и стоит в своей.

Отклонено:

- заливка ячейки таблицы на всю ширину колонки: три залитые ячейки в строке спорят со статусом за внимание;
- цветная точка рядом с названием: цвета слишком мало, чтобы прочитать его с одного взгляда;
- условные классы в каждом шаблоне: правило оказалось бы в трёх местах.

### 6. Строка списка и ширина страницы

Колонки таблицы по порядку: номер, запрос, вид операции, приоритет, сумма, форма оплаты, статус, дедлайн, подан.

- Ячейка «Запрос»: первая строка ситуации ссылкой на запрос, под ней автор, если автор не тот, кто смотрит.
- Вид операции и приоритет стоят перед суммой. Форма оплаты стоит сразу после суммы: «сколько» и «как платить» читаются вместе.
- Карточка на узком экране: первая строка ситуации и сумма, под ними три значения в том же порядке, ниже статус и сторона.
- Все страницы расширяются до 1280 px: `max-w-7xl` в шапке и в основном блоке общего layout.
- На странице запроса колонка запроса вырастает до 864 px. Текст ситуации и решения ограничен шириной 768 px (`max-w-3xl`), чтобы строка осталась близкой к нынешним 736 px. Остальные блоки колонки занимают её целиком.
- На странице «Справочники» три карточки делят новую ширину поровну, их содержимое не меняется.

Отклонено:

- расширить только страницу списка: шапка и содержимое стояли бы на разной ширине на разных страницах, и при переходе логотип и меню прыгали бы;

- вид операции заголовком строки и ещё раз колонкой: одно значение показано дважды;
- три значения строкой под заголовком, без своих колонок: значения одного справочника не выстраиваются по вертикали, и колонку нельзя пробежать глазами;
- прежняя ширина 1152 px: колонке «Запрос» остаётся 204 px, и первая строка ситуации обрезается уже на 29 знаках.

### 7. Палитра открывается под значением

На странице «Справочники» перед названием значения стоит кружок его цвета, у значения без цвета кружок пустой с пунктирной границей. Нажатие открывает под значением девять вариантов в два столбца: «без цвета» и восемь цветов палитры. У каждого варианта кружок цвета и название цвета текстом, выбранный отмечен галочкой. Выбор сразу отправляет `PATCH` и закрывает палитру.

Варианты размечены как группа переключателей, названия берутся из локалей. Какая палитра открыта, хранит локальное состояние страницы, так же как идентификатор значения, которое сейчас переименовывают.

Отклонено:

- ряд кружков без подписей: варианты различались бы только цветом, а название пряталось бы во всплывающей подсказке, которой нет на сенсорном экране;
- всплывающая панель: такого компонента в интерфейсе нет, и заводить его ради одного списка вариантов незачем;
- системный выбор цвета (`input type="color"`): он отдаёт произвольный код цвета, а не цвет палитры.

### 8. Что меняется в существующем коде

- Вывод названия значения в трёх шаблонах (строка списка, карточка списка, страница запроса) заменяется компонентом `ReferenceValue`.
- Общий layout получает новую ширину, текст ситуации и решения на странице запроса получает ограничение ширины.
- Сервис и контроллер справочников не получают новой логики: проверку делает схема, запись делает базовый сервис.
- Не трогаются: `StatusBadge`, таблица `DOTS` журнала, форма запроса.

## Risks / Trade-offs

- [Оттенок значения совпал с оттенком статуса в той же строке] → статус круглый и стоит в колонке статуса, значение прямоугольное и стоит в своей колонке.
- [Финансовый директор раскрасил все значения, и список стал пёстрым] → значение без цвета остаётся текстом, палитра ограничена восемью цветами, цвет снимается одним нажатием.
- [Человек не различает цвета] → название значения всегда показано текстом, в палитре у каждого варианта подписано название цвета.
- [Имя цвета убрали из палитры или переименовали, а в базе оно осталось] → чтение каждого запроса с таким значением не пройдёт проверку ответа. Имена только добавляются, а удаление и переименование идут с миграцией сохранённых значений.
- [На экране от 640 до 1280 px девять колонок не помещаются] → первая строка ситуации обрезается многоточием, таблица прокручивается по горизонтали в своём контейнере.
- [Во время выката новый интерфейс получает ответ старого сервера без поля цвета] → значения показаны без цвета, пока сервер не обновится. Действия с запросами от цвета не зависят.

## Migration Plan

Миграция `0002` добавляет таблице значений справочников колонку цвета, допускающую `NULL`. Существующие значения остаются без цвета. Откат удаляет колонку вместе с заданными цветами.
