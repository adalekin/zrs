# access-and-roles Specification

## Purpose
Вход через провайдера организации и четыре роли определяют, кто попадает в сервис и что в нём может делать. Учётные записи и пароли сервис не хранит.

## Requirements

### Requirement: Вход через провайдера организации

Система SHALL пускать человека только после входа через провайдера OpenID Connect, заданного установкой.

Организация уже ведёт учётные записи в своём провайдере, вторая база паролей ей не нужна.

#### Scenario: Человек открывает сервис без входа

- **WHEN** человек открывает любую страницу сервиса без действующего входа
- **THEN** сервис отправляет его на вход к провайдеру и после входа возвращает на ту же страницу

#### Scenario: Обращение к API без входа

- **WHEN** к API приходит обращение без подтверждения входа
- **THEN** система отказывает и не отдаёт данных

#### Scenario: Выход

- **WHEN** человек выходит из сервиса
- **THEN** его вход прекращается и в сервисе, и у провайдера

### Requirement: Проверка подтверждения входа

Система SHALL принимать подтверждение входа только если оно подписано провайдером установки, выпущено для этой установки и срок его действия не истёк.

У одного провайдера бывает много приложений, и вход в другое приложение не должен открывать запросы на расход.

#### Scenario: Подтверждение от другого провайдера

- **WHEN** к API приходит подтверждение входа, выпущенное другим провайдером
- **THEN** система отказывает

#### Scenario: Подтверждение для другого приложения

- **WHEN** к API приходит подтверждение входа от провайдера установки, выпущенное для другого приложения
- **THEN** система отказывает

#### Scenario: Истёкший срок

- **WHEN** к API приходит подтверждение входа с истёкшим сроком действия
- **THEN** система отказывает

### Requirement: Четыре роли

Система SHALL различать четыре роли: сотрудник, модератор, финансовый директор, исполнитель выплаты. Роли человека система SHALL брать из сведений провайдера при каждом входе по соответствию, заданному установкой. У человека может быть несколько ролей.

Роли раздаёт организация в своём провайдере, там же, где она управляет остальными доступами.

#### Scenario: Человек с двумя ролями

- **WHEN** входит человек, которому провайдер сообщает роли сотрудника и модератора
- **THEN** ему доступны действия обеих ролей

#### Scenario: Роль другого приложения

- **WHEN** входит человек, у которого в сведениях провайдера есть только роли, не указанные в соответствии установки
- **THEN** сервис сообщает, что доступа нет, и не показывает запросы

#### Scenario: Человек без ролей

- **WHEN** входит человек, которому провайдер не сообщает ни одной роли
- **THEN** сервис сообщает, что доступа нет, и не показывает запросы

#### Scenario: Роль сняли

- **WHEN** у человека сняли роль модератора в провайдере, и он вошёл снова
- **THEN** действия модератора ему больше недоступны

### Requirement: Список людей

Система SHALL вести список людей, которые входили в сервис: имя и роли на момент последнего входа. Список служит только для выбора модератора и для показа имён в запросах и журнале.

Автор выбирает модератора из людей, а узнать о человеке сервис может только при его входе.

#### Scenario: Первый вход модератора

- **WHEN** человек с ролью модератора впервые входит в сервис
- **THEN** авторы видят его в списке модераторов

#### Scenario: Модератор потерял роль

- **WHEN** человек, у которого сняли роль модератора, входит снова
- **THEN** авторы больше не видят его в списке модераторов

#### Scenario: Провайдер не сообщил имя нового человека

- **WHEN** человек впервые входит в сервис, а провайдер не отдаёт сведения о нём
- **THEN** сервис сообщает, что временно недоступен, и не добавляет человека в список без имени

#### Scenario: Имя в журнале

- **WHEN** человек открывает журнал запроса
- **THEN** у каждой записи показано имя того, кто её оставил
